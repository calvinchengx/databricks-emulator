# v0.2.5

A correction. v0.2.4 advertised decimal columns to Unity Catalog as `DOUBLE`,
and said the Delta files still held the engine type. The first half worked and
the second half was true only of the table that was registered — which is not
where the damage landed.

```
docker pull ghcr.io/calvinchengx/databricks-emulator:0.2.5
```

## Decimal columns

Anything reading a registered table *through UC* received a double, so every
table DERIVED from it was written physically double. Measured on Contoso gold:
`fct_sales.amount_usd` is `decimal(19,4)` in its own Delta log while `typeof()`
answers `double`, and the summary built from it holds double on disk. A money
column had stopped being money, and no row-count or aggregate check can see
that — the numbers still add up.

The root cause was not the `DOUBLE` mapping. It was registering column metadata
into UC **at all**. Measured four ways over the same Delta bytes:

| registered as | result |
|---|---|
| no columns | Sail reads the Delta log and gets `decimal(19,4)` |
| `DOUBLE` columns | Sail binds the column as double |
| `decimal(19,4)` columns | Sail refuses — `Unsupported complex type` |
| a `_col` placeholder | the table is unreadable |

EXTERNAL registration now sends **no columns**. The Delta log at
`storage_location` is the authoritative schema and Sail reads it from there, so
the second copy in UC was never needed — it could only disagree. Tables that
were never described already behaved this way; they were the ones that worked.

## What this does not fix

Sail's unity catalog provider still rejects `decimal(p,s)` in UC column
metadata (`Unsupported complex type`). This release stops the emulator relying
on that mapping; it does not make Sail accept it. If a future change needs
columns in UC, the decimal problem returns and belongs upstream.

Pull `0.2.5` if you build gold models over decimal facts — particularly if a
contract asserts money is not stored as float, which `0.2.4` would fail for a
reason invisible in the data.
