# v0.2.5

Decimal columns are decimal again. A money column had stopped being money
in every table derived from a registered one, and no row check could see it.

```
docker pull ghcr.io/calvinchengx/databricks-emulator:0.2.5
```

## Decimal columns read as float (#46)

v0.2.4 advertised `DOUBLE` for decimal columns when registering an EXTERNAL
table, because Sail's unity catalog provider refuses a three-part read of
`decimal(p,s)` outright (`Unsupported complex type`). That note said the Delta
files still held the engine type. They did — but that is not where the damage
landed. **Anything reading such a table through Unity Catalog got a double**,
so every table derived from one was written physically double.

Measured on a gold star built by dbt: `fct_sales.amount_usd` was
`decimal(19,4)` in its own Delta log while `typeof()` answered `double`, and
the summary aggregated from it held `double` on disk. Downstream, a revenue
total arrived as `129341157.67000002` where a Fabric runtime on identical
inputs reported `129341157.6700`.

The cause was not the `DOUBLE` mapping itself but registering column metadata
at all. Four registrations over the same Delta bytes:

| UC registration | Sail read |
|---|---|
| no columns | `decimal(19,4)` — reads the Delta log |
| `DOUBLE` columns | reads, and **binds the column as double** |
| `decimal(19,4)` columns | refuses: `Unsupported complex type` |
| `_col` placeholder | unreadable — real columns missing from the schema |

So registration now carries **no column metadata**. The Delta log at
`storage_location` is the authoritative schema and Sail reads it there; a
second, lossy copy in UC is what created the defect. After the change, on a
rebuilt star:

```
fct_sales.amount_usd                      decimal(19,4)
fct_revenue_summary.revenue_usd           decimal(29,4)
fct_revenue_summary.cancelled_revenue_usd decimal(29,4)
dim_product.list_price_usd                decimal(19,4)
```

`decimal(29,4)` is what real Spark produces summing `decimal(19,4)`, so the
aggregate is money on disk rather than merely holding the right number.

**This also rules out `sum()`**, which was blamed first: a fresh
`sum(CAST(1.5 AS DECIMAL(19,4)))` returns `decimal(29,4)` correctly. The
columns were already double before `sum()` saw them.

### The trade, stated

Unity Catalog now serves **less metadata than real Databricks**, in exchange
for types that are correct. Wrong types change query results; absent metadata
does not, and nothing reads it here — `information_schema.columns` is empty
either way. Restore the description when Sail's unity provider can express
decimal; `pysail` 0.7.0, the current release, cannot.

### Also

The `_col` STRING placeholder is gone. It stood in when `DESCRIBE` failed, but
Unity Catalog accepts an empty column list and a table registered with the
placeholder is **unreadable** — Sail binds only `_col`, so every real column
"is missing from the schema".

`ColumnsFromDescribe` and `sparkToUC` are deleted rather than left unused: dead
code that encodes the exact defect is a trap. Two regression tests fail if
columns, or a mapped `DOUBLE`, come back.
